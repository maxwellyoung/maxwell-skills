# Cache headers

Make repeat visits and in-site navigations cost almost no bytes by giving every response the caching policy that matches what it actually is. Measure first, classify each response type, set policy per type, prove it on a preview deployment against a baseline, and re-measure. A faster cache that shows someone stale or private content is a failure, not a trade-off.

## Rules

- **Behaviour is the contract.** Users must never see stale, mixed-version or another user's content because of a caching change. Any change in freshness, personalisation or correctness is a regression unless the user approves it. For every change, report what it saves and what it risks (the longest time a user could see an old version).
- **Private beats fast.** When unsure whether a response is personalised, treat it as personalised. A leaked page cannot be recalled: `Clear-Site-Data: "cache"` clears only the browser, and nothing clears another user's copy in a shared cache except a purge.
- **Long lifetimes only for content-addressed URLs.** A one-year `max-age` is a promise that the bytes at that URL will never change. Only a content hash in the path or filename keeps that promise.
- **Authority.** Header changes reach users only through a deploy, and deploys need the user's explicit approval. So do CDN purges, cache rules and dashboard settings on hosting providers. Work locally and on preview URLs the user provides. Before any approved rollout, record the previous config and a purge plan so it can be rolled back.
- **Check the host, don't assume it.** Hosts and CDNs rewrite, strip and override caching headers, and their defaults change. Read the current docs for the host in use, then confirm with real responses. `references/hosts.md` lists what to look for.

## 1. Measure the current state

Record this on production (read-only `GET`/`HEAD`) and on a preview built from the same commit, and keep it for the report. Preview and production often differ (preview may be uncached, password-protected, or on a different CDN config), so note which one each observation comes from.

- **Inventory every response type** from the built output, the router config and a crawl, not just the obvious pages: HTML documents (static, ISR/revalidated, server-rendered, logged-in), API/JSON, framework data payloads (Next.js RSC flight data, `_next/data`, loader/`__data.json` endpoints), hashed build assets, unhashed files in `/public` or `static/`, fonts, images and image-optimiser output, video and `Range` responses, the service worker script and its imports, the web manifest and icons, `robots.txt`, `sitemap.xml`, feeds, `.well-known/` files, redirects (301, 302, 307, 308), 404 and 410 pages, error pages, and anything proxied from another origin.
- **Per response record:** status, `Cache-Control`, any `CDN-Cache-Control` or host-specific variant that reaches the client, `Expires`, `ETag` (strong or weak), `Last-Modified`, `Vary`, `Age`, `Set-Cookie`, `Content-Type`, `Content-Encoding` (br, gzip, zstd or none), `Content-Length`, and the CDN status header (`x-vercel-cache`, `cf-cache-status`, `Cache-Status`, `x-cache`). Use `curl -sSI` with and without `Accept-Encoding: br, gzip`, and with a real `GET` where `HEAD` is handled differently.
- **Per page:** first-visit bytes, repeat-navigation bytes and reload bytes, with request counts and how many were 200, 304 or served from cache (see step 5 for the method).
- **Where headers come from:** framework defaults, `next.config` / `vercel.json` / `netlify.toml` / `_headers` / nginx config / S3 object metadata / CloudFront policy / Cloudflare cache rules, middleware, and per-route code. Note which layer wins on this host.

## 2. Classify each response

For each type, answer before choosing a policy:

- **Is the URL content-addressed?** A hash of the content in the path or filename (`app.3f9a1c.js`) qualifies. A build ID shared by every file, a `?v=` you bump by hand, or a timestamp does not, unless you have confirmed it changes whenever the bytes do. Check that the CDN keeps query strings in its cache key if the version lives there.
- **Can it differ per user, session, cookie, `Authorization`, A/B bucket, geography, language, device or feature flag?** Read the handler and the middleware, not the route name. Rendering the user's name, cart count, CSRF token, CSP nonce or a "signed in" header counts.
- **Does it set a cookie?** Session refresh, analytics, A/B and consent middleware often add `Set-Cookie` to every response, including ones you meant to be public.
- **Does it share a URL with another representation?** HTML and framework data on the same path, WebP/AVIF negotiated by `Accept`, compressed variants, mobile layouts by header.
- **How stale may it be, and who decides?** Get an explicit window for each type that is not content-addressed. "Changes on deploy", "within a minute of a CMS publish" and "never stale" lead to different policies.

## 3. Set the policy per type

- **Hashed build assets:** `Cache-Control: public, max-age=31536000, immutable`. `immutable` saves the revalidation on reload in browsers that honour it; Chrome does not implement it but already skips revalidating subresources on reload. Many frameworks set this themselves (Next.js does for its hashed assets and does not allow overriding it), so confirm rather than duplicate.
- **Unhashed assets** (`/public/logo.svg`, `/og.png`, PDFs, downloads): never a long `max-age`, because an update stays stale in every browser that has it until expiry and nothing can recall it. Prefer moving them into the bundler so they get hashed URLs. Otherwise use `no-cache` (store, but revalidate every use) or a short `max-age` the user accepts, with stable validators. Keep URLs that are linked from outside (OG images, favicons, emailed PDFs) at a fixed path and revalidated.
- **HTML documents:** usually `no-cache` (or `max-age=0, must-revalidate`) for the browser so a deploy reaches the next navigation, with shared-cache caching via `s-maxage` or a CDN-targeted header if the page is the same for every visitor. `no-cache` does not mean "don't store", and it does not affect bfcache; `no-store` can (see step 4). A short browser `max-age` (tens of seconds) is a deliberate staleness trade the user must accept.
- **`stale-while-revalidate`:** serves a stale copy while fetching a fresh one in the background, so it lengthens the window in which a user can see old content by its value. Browsers support it in their HTTP caches (Chromium, Firefox, Safari 14+). CDN support differs: Vercel, Netlify, CloudFront, current Cloudflare and nginx (with `proxy_cache_use_stale updating` and `proxy_cache_background_update`) honour it in their own ways, and some strip it before the browser sees it. `stale-if-error` similarly keeps old content alive during outages. Add each only with an agreed window.
- **Browser versus shared cache:** `max-age` applies to both unless overridden; `s-maxage` applies only to shared caches; `CDN-Cache-Control` (RFC 9213) targets CDNs and is passed downstream; host-specific headers (`Vercel-CDN-Cache-Control`, `Netlify-CDN-Cache-Control`, `Cloudflare-CDN-Cache-Control`) target one CDN and are usually not forwarded. Precedence and stripping are host-specific. Some hosts remove `s-maxage` or `stale-while-revalidate` from what the browser receives, so the header you see in the browser is not the policy the CDN applied. Check the host's docs and confirm with `curl` plus the CDN status header.
- **Personalised or authenticated responses:** `Cache-Control: private` (browser may store) or `no-store` (nothing stores; use for account, billing, health, admin, tokens, and anything that must not survive logout on a shared machine). Never `public`: per RFC 9111 `public`, `s-maxage` and `must-revalidate` let a shared cache store a response to a request carrying `Authorization`. Set it in the handler that knows the response is personal, not by route pattern alone.
- **API/JSON:** public, rarely changing reads may take `s-maxage` with a short browser `max-age`; per-user reads are `private` or `no-store`; mutations are never cached. Check that `GET` endpoints with side effects are not suddenly cacheable.
- **Service worker script:** serve `/sw.js` with `no-cache` or `max-age=0`. With the default `updateViaCache: 'imports'` the main script bypasses the HTTP cache on update checks but its `importScripts` do not, so imported scripts must be hashed or revalidated. Never let a CDN pin the worker for long.
- **Manifest, icons, `robots.txt`, `sitemap.xml`, feeds, `.well-known/`:** short lifetimes with revalidation. Cloudflare caches `robots.txt` by default; make sure crawl rules and sitemaps update on the timescale the user expects.
- **Redirects:** browsers may keep a 301 or 308 indefinitely, and without explicit headers CDNs cache them by default (Cloudflare caches 301 for two hours). Add `Cache-Control` to permanent redirects deliberately, and use 302/307 for anything still being tested.
- **404 and 410:** a cached 404 hides a page published moments later, and a cached 404 for a hashed asset becomes permanent. Keep 404 lifetimes short, and make sure long-lived asset rules apply only to successful responses (nginx `add_header` without `always` already applies only to 2xx/3xx; host path rules often do not distinguish).
- **Images and image-optimiser output:** hashed or content-addressed variants can be long-lived. If the format is negotiated from `Accept`, the cache must key on it: `Vary: Accept` from the origin, or the CDN's image feature. A CDN that ignores `Vary` will serve AVIF to a browser that asked for JPEG.
- **Compression:** keep `Content-Encoding` working on every text type and `Vary: Accept-Encoding` on negotiated responses. Report bytes over the wire, not decoded size.
- **No headers at all:** a response with `Last-Modified` and no `Cache-Control` is cached heuristically (typically 10% of its age since modification), so an old unhashed file can be reused for weeks. Give every response an explicit policy, including error pages and anything served by a fallback route.

## 4. Edge cases to check before proving

- **`Set-Cookie` on a cacheable response.** RFC 9111 says `Set-Cookie` does not inhibit caching. Vercel, nginx `proxy_cache` and Cloudflare with origin cache control refuse to cache it; other caches may store the cookie with the response and hand one user's session to everyone. Remove the cookie from public responses or make them `private`. Check middleware that refreshes sessions on every request.
- **`Vary`.** `Vary: Cookie` on a shared-cache response either kills the hit rate or, on some hosts, disables caching entirely (Vercel refuses to cache it); prefer `private` for per-user content and a narrow header or a specific cookie key (`Netlify-Vary: cookie=...`) for buckets. `Vary: User-Agent` fragments the cache across every browser build. `Vary: *` is effectively uncacheable. Cloudflare ignores most `Vary` values by default, so a response that depends on a request header other than `Accept-Encoding` is unsafe to cache there without a cache rule.
- **Same URL, different representations.** App Router RSC payloads, data endpoints and HTML that share a path and differ by request header rely on `Vary` and framework cache keys. A CDN rule such as "cache everything" that ignores those can serve flight data as a page or the wrong page to a client navigation. Test client-side navigation and full loads after the change.
- **Deploy skew.** HTML cached anywhere (CDN, browser, service worker, a tab left open) references hashed assets from its own build. If the new deploy deletes them, lazy chunks 404 and the app breaks mid-session. Keep previous builds' assets available for at least the longest HTML lifetime plus typical session length (host skew protection, such as Vercel's, or uploading assets additively), and never cache HTML longer than old assets are retained.
- **SPA fallbacks.** A catch-all that returns `index.html` with 200 for a missing `/assets/app.abc.js`, under a path rule that sets a one-year `immutable`, pins broken HTML-as-JavaScript in browsers for a year. Missing hashed assets must return a real 404 with a short lifetime.
- **Service worker caches.** A cache-first worker overrides every HTTP header and can pin an old HTML shell and its assets indefinitely. Inventory what it precaches and how it updates (`skipWaiting`, `clients.claim`, versioned cache names, deletion of old caches) before changing HTTP policy, and include it in the stale-content test.
- **bfcache.** `Cache-Control: no-store` on the HTML document can make a page ineligible for the back/forward cache. Chrome now admits `no-store` pages in limited cases (evicted when cookies change, shorter timeout); other browsers may still exclude them. Use `no-store` on HTML only for genuinely sensitive pages, and check current browser behaviour and the DevTools bfcache panel before claiming a bfcache effect either way.
- **Revalidation cost.** A 304 is small but still a round trip per resource. Long `max-age` on hashed assets removes them; `no-cache` on many unhashed files keeps them. Validators must be stable: ETags derived from inode or per-server state, or `Last-Modified` reset by every build or container copy, turn every revalidation into a full 200. Compression layers may weaken a strong ETag; that is fine for `If-None-Match`.
- **Shared-cache overrides.** CloudFront with a minimum TTL above 0 caches responses marked `private`, `no-store` or `no-cache` for that minimum. Cloudflare's Browser Cache TTL raises origin `max-age` values shorter than its setting. Netlify's CDN caches static files for a year at the edge and invalidates on deploy, while the browser gets `max-age=0, must-revalidate`. Basic auth on Netlify disables caching site-wide. Check these settings on the host before trusting origin headers.
- **Preview is not production.** Preview deployments may bypass the CDN, sit behind authentication cookies (which make responses uncacheable), or use different rules. Know which differences apply, and say which results only production can confirm.

## 5. Prove it on the preview deployment

1. **Baseline.** Run the same matrix and browser measurements on a preview of the unchanged commit (or production, read-only) so before and after differ only in caching config.
2. **Header matrix.** `curl -sSI` (and `GET` with `-o /dev/null -D -`) every response type on the preview, each as anonymous, with a session cookie, and with `Authorization` where APIs use it, with and without `Accept-Encoding` and alternative `Accept` values for images. Request each twice and record the CDN status on the second: public types should hit, private ones must never show a hit. Save the table.
3. **Repeat-visit bytes.** In Playwright, use `chromium.launchPersistentContext(userDataDir)` so the HTTP cache survives between runs, with no `page.route` handlers (routing disables the HTTP cache) and service workers left as production runs them. Measure: first visit, a second navigation to the same page in the same context, a navigation to another page, a fresh launch with the same profile, and `page.reload()`. Record per run the transferred bytes (CDP `Network.loadingFinished` `encodedDataLength`), request count, and 200/304/cache split from `Network.responseReceived` (`fromDiskCache`, `fromServiceWorker`).
4. **Stale-content test.** With the user's approval for a preview deploy, deploy a visible change (a text marker in HTML, a changed unhashed file, a data change) to the same preview URL. From a warm browser profile and through the CDN, confirm the new version appears within each type's agreed window and that no page mixes old HTML with missing assets. Repeat the open-tab case: load, deploy, then navigate client-side and trigger a lazy chunk.
5. **Private-data test.** Request a personalised page and API as a logged-in user twice, then immediately as an anonymous request (and as a second user) from a different client. The anonymous and second-user responses must never contain the first user's data, and must not show a cache hit for a personalised response. Repeat after logout and with the back button.
6. **Re-measure** the step 1 metrics and compare per type and per page.

## Report back

- A table per response type: old and new headers, CDN status on second request, and the agreed staleness window.
- Bytes and requests per page for first visit, repeat navigation, fresh launch and reload, before and after, with the 200/304/cache split.
- Stale-content and private-data test results, with the exact requests used.
- What each change saves and what it risks, and every deviation from the request with its cost.
- What was verified on preview only, what needs production confirmation, and the rollback: previous config, purge commands, and whether a purge is needed (browser caches cannot be purged).

**Later (proposals, not part of the default change):** CDN caching of shared HTML with tag-based purge on content publish, moving unhashed assets into the bundler, enabling the host's skew protection, `stale-if-error` for outage resilience, and a service worker review. Weigh each against freshness, cost and leak risk before proposing it.
